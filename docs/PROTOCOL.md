# Gateway WebSocket protocol v1

This document defines the adapter-to-Gateway contract. It is a JSON text protocol over WSS; it does not promise resumable streams. The shared TypeScript package is the implementation source for the schemas and constants, while these examples are the reviewable wire contract.

## Connection and authentication

The adapter connects to the configured Gateway WebSocket path using TLS, offers the subprotocol `llm-proxy.v1`, and sends `Authorization: Bearer <access-token>` in the HTTP upgrade request. Access tokens never appear in URLs, query strings, or subprotocol values. The token is a five-minute ES256 JWT with the configured machine-token issuer, `aud=llm-socket-gateway`, and claims described in [ADR 0001](decisions/0001-phase-1-contracts.md).

Gateway calls Identity's private `IdentityInternal.validateToken(accessToken)` Service Binding method before upgrading. Identity verifies the JWT signature and JOSE header against its configured public JWKS, checks issuer, audience, time claims, and active session/client/user/project, then returns verified claims and `tokenExpiresAt`. Identity permits at most five seconds of clock skew. Gateway checks that the RPC result has the configured issuer and expected audience, required claim shapes, no more than 30 seconds of future `iat`/`nbf`, and `exp > now` strictly. Identity exposes no public `/internal/*` HTTP endpoint. The binding is a `[[services]]` entry with `binding="IDENTITY"` and `entrypoint="IdentityInternal"`; the configured service name is environment-specific. Gateway sends `session.ready` only after these checks succeed. Prefer an HTTP 401/403 response before upgrade for failed authentication. If the runtime has already upgraded, close with policy code 1008 and do not send `session.ready`. On every request start Identity verifies the JWT and active delegation again. A successful socket is authorized to start new requests only until `tokenExpiresAt`; the browser's OIDC cookie is not a Gateway credential.

All frames are JSON objects encoded as UTF-8 text. Binary frames, invalid JSON, unknown event names, and schema violations are protocol errors. `requestId` is a canonical UUID generated by the adapter. It is unique across the entire socket, including after a request has ended. Gateway remembers up to 1,024 IDs; after that it sends `session.draining` for policy and closes after active work finishes. Reusing an ID is a protocol error and closes the socket with 1002.

## Server to client

After authentication:

```json
{
  "event": "session.ready",
  "protocol": 1,
  "connectionId": "opaque-server-generated-id",
  "maxInFlight": 8,
  "maxPayloadBytes": 1048576,
  "maxSessionSeconds": 300,
  "maxChunkBytes": 32768,
  "ackWindow": 8,
  "maxRequestFrameBytes": 1048576,
  "maxResponseFrameBytes": 262144,
  "tokenExpiresAt": 1792243500
}
```

`connectionId` is for diagnostics and is not an authorization secret. `maxInFlight` is the project concurrency limit, capped at eight. `maxPayloadBytes` is the project limit on the UTF-8 serialized provider JSON body after Gateway inserts the authorized upstream model and `stream:true`; it excludes the envelope and WebSocket framing and is capped at 1 MiB. `maxSessionSeconds` is the project socket lifetime measured from attach, capped at 300 seconds. At that deadline Gateway sends policy draining and closes the socket, cancelling active work. `maxChunkBytes` bounds the UTF-8 bytes in `response.chunk.data`; JSON framing can add overhead. The full serialized `response.chunk` frame is capped at 256 KiB. Reject any received text frame larger than 1 MiB and any control frame other than `response.chunk` larger than 4 KiB. Start payload JSON is limited to depth 64 and 65,536 values.

Each streamed provider text segment is sent as:

```json
{
  "event": "response.chunk",
  "requestId": "3a0d1ae4-6c1d-4f4a-9c93-b5be26646a01",
  "seq": 0,
  "data": "event: message_start\ndata: {\"type\":\"message_start\"}\n\n"
}
```

`data` is the raw UTF-8 text read from the provider's streaming response. It is not parsed, normalized, or interpreted by Gateway. A source read can be split into several protocol chunks; chunks never split a UTF-8 code point. `seq` begins at zero and increases by one for each request. Empty `data` is invalid. The v1 schema permits up to 32 KiB of `data`; Gateway currently emits at most 16 KiB UTF-8 per chunk. The full serialized frame is capped at 256 KiB, and total provider response text at 16 MiB per request; reaching the total cap aborts upstream and returns `response.error` with `code="response_too_large"`.

Successful completion is:

```json
{
  "event": "response.end",
  "requestId": "3a0d1ae4-6c1d-4f4a-9c93-b5be26646a01",
  "lastSeq": 4,
  "usage": { "inputTokens": 120, "outputTokens": 45, "totalTokens": 165 }
}
```

`lastSeq` is the last chunk sequence sent, or `-1` when no chunk was sent. This event means Gateway read the upstream HTTP body to EOF; it does not certify that the provider's application-level stream was complete. Because Gateway forwards provider SSE unchanged, the adapter's provider parser must see that provider's success sentinel before it reports local SSE success: for example, OpenAI Chat Completions `[DONE]` or Anthropic Messages `message_stop`. If EOF arrives without a valid sentinel, the adapter surfaces an interrupted/invalid upstream stream and does not emit a successful local `[DONE]`. `usage` is omitted if the provider did not report trustworthy counts. Gateway does not estimate or persist token usage in this protocol.

A failed request is:

```json
{
  "event": "response.error",
  "requestId": "3a0d1ae4-6c1d-4f4a-9c93-b5be26646a01",
  "lastSeq": 2,
  "code": "upstream_rate_limited",
  "message": "The provider is rate limiting this request.",
  "upstreamStarted": true,
  "retryable": true
}
```

`lastSeq` has the same meaning as on `response.end`. `upstreamStarted` is true as soon as Gateway starts the provider fetch; the provider may already have processed or billed the attempt even when no response chunk arrived. `retryable` means the condition may be transient, not that replay is safe. Gateway never retries. A client retry is a new attempt with a new `requestId`; it must not append to or merge with the old stream. `message` is short, safe text and never contains the raw provider response, key, envelope, request payload, or internal stack trace.

The v1 `code` values are `invalid_request`, `unauthorized`, `forbidden`, `credential_invalid`, `provider_disallowed`, `model_disallowed`, `overloaded`, `upstream_rate_limited`, `upstream_error`, `upstream_timeout`, `response_too_large`, `slow_client`, `cancelled`, `session_expired`, and `internal_error`. Only the relevant request receives a terminal error. Do not expose provider response bodies or raw authentication data in error messages. Authenticated clients may receive bounded HTTP status and fixed allowlisted rejection categories, including credential, workspace, budget and model policy, as defined in ADR 0003; arbitrary provider descriptions are excluded.

When a token approaches expiry, the server sends:

```json
{
  "event": "session.draining",
  "reason": "token_expiring",
  "reconnectAfterMs": 0
}
```

`reason` is `token_expiring`, `server_shutdown`, or `policy`. Upon draining the adapter stops starting requests and obtains a fresh token before reconnecting. Gateway rejects new starts at token expiry. A request already authorized may continue only until the earlier of its 300-second request deadline and the hard `maxSessionSeconds` socket lifetime. Token expiry itself does not cancel that request.

## Client to server

### Start a request

```json
{
  "event": "request.start",
  "requestId": "3a0d1ae4-6c1d-4f4a-9c93-b5be26646a01",
  "provider": "openai",
  "model": "fast-chat",
  "envelope": {
    "v": 1,
    "alg": "A256GCM",
    "kid": "env-2026-10",
    "credentialId": "cred_01J...",
    "userId": "usr_01J...",
    "projectId": "prj_01J...",
    "provider": "openai",
    "exp": 1794835500,
    "nonce": "B64URL_NONCE",
    "ciphertext": "B64URL_CIPHERTEXT_AND_TAG"
  },
  "payload": {
    "messages": [{ "role": "user", "content": "Hello" }],
    "temperature": 0.2
  }
}
```

The envelope encoding and AES-GCM associated data are defined in [ADR 0001](decisions/0001-phase-1-contracts.md). The envelope is included on every start, is sensitive bearer material, and is not accepted as authorization by itself. For every start, Gateway calls `IdentityInternal.authorizeTokenRequest({accessToken,credentialId,provider,model})`; Identity derives all principal fields from the verified token, then checks active session/client/user/project ownership and current credential/provider/model state in D1. It returns verified principal, credential metadata and the authorized registry provider route (ID, protocol and Base URL). The route is read from D1; client input cannot replace it. Gateway compares that result with the authenticated envelope before decryption. A tampered, expired, revoked, or cross-owner envelope is rejected.

`provider` is a configured provider ID. `model` is an application alias authorized for the principal. `payload` is a provider-specific JSON object produced by the adapter, excluding endpoint URL, model, and streaming mode. The shared schema bounds JSON depth and size and rejects server-owned fields; Gateway checks the serialized provider body against the project and hard byte limits after injecting the server-mapped upstream model and forcing streaming. Provider-format translation and request construction belong to the adapter and trusted provider-specific routing code. The WebSocket frame is limited to 1 MiB including the envelope. Gateway never accepts a client-selected URL, hostname, path, redirect, authentication header, or arbitrary upstream model.

Only configured HTTPS provider endpoints are callable. The endpoint, path, provider authentication-header rule, and alias-to-upstream-model mapping live in server-side configuration. Redirects are disabled; a redirect response is treated as an upstream error. The MVP uses explicit provider definitions (for example, the configured official OpenAI or Anthropic API endpoint); adding a custom endpoint requires administrator allowlisting and SSRF review. The provider registry—not data in `payload`—determines routing.

At most `maxInFlight` requests may be active on a socket, up to the hard cap of eight. A start beyond that limit receives `response.error` with `code="overloaded"`. A valid start is authorized afresh by Identity before decrypting the envelope and calling a provider. Gateway rejects a provider JSON body larger than the lower of `maxPayloadBytes` and the hard 1 MiB cap. Request time is limited to 300 seconds, and a provider fetch or stream read that remains idle for 60 seconds fails with `upstream_timeout`. When no request is active, Gateway closes the socket after 60 seconds. The WebSocket protocol does not guarantee account-wide concurrency limits across separate sockets.

### Acknowledge response data

Workers do not provide a reliable, portable signal that a WebSocket's outbound queue has drained. Protocol v1 therefore uses an acknowledgement variant of the existing `request.start` event, keeping the seven event names fixed:

```json
{
  "event": "request.start",
  "op": "ack",
  "requestId": "3a0d1ae4-6c1d-4f4a-9c93-b5be26646a01",
  "ackSeq": 0
}
```

Normal start frames omit `op`. For ACK frames, `ackSeq` is the highest contiguous `response.chunk.seq` fully consumed by the adapter's local response writer. The adapter ACKs only after its local writer accepts the bytes and, when it signals backpressure, after its `drain` event. The initial acknowledged sequence is `-1`, so the first ACK is `0`. ACKs are cumulative and bound to both the same socket and `requestId`. A duplicate or older ACK is harmless; an ACK beyond the highest sequence sent is a protocol error and closes the socket with 1002. An ACK for an ID never started on this socket is also a protocol error. After a terminal frame, Gateway continues to accept ACKs for that request while any previously sent chunks remain unacknowledged; these ACKs release only the tracked pending-frame budget, not the cumulative lifetime outbound cap. Once those chunks are acknowledged, later ACKs for the known request ID are ignored.

Gateway sends no more than eight unacknowledged chunks per request. Its emitted chunk data is at most 16 KiB UTF-8 (the v1 schema allows 32 KiB), and its tracked pending serialized response-chunk budget is capped at 4 MiB per socket. When either per-request credit or the pending-frame budget is full, Gateway pauses provider reads until an ACK arrives. A request remains active after its terminal frame while chunks remain unacknowledged, so completed streams continue to count toward the eight-request socket limit. The oldest outstanding chunk has a 15-second acknowledgement deadline. Before a terminal frame, timeout aborts upstream, attempts one `response.error` with `code="slow_client"`, sends `session.draining` with `reason="policy"`, and closes the entire socket with code 1013. If a terminal frame was already sent, timeout closes with 1013 without a second terminal frame. This can interrupt other requests on the same socket. With eight active requests, the application-level maximum unacknowledged chunk text is 1 MiB, plus at most 4 MiB of tracked serialized chunk frames. Independently, Gateway enforces an 8 MiB cumulative serialized outbound-frame budget per socket lifetime. It counts every frame, including control and terminal frames, and ACKs never refund it. Gateway reserves room for a policy-draining frame when possible; at the cap it aborts active work and closes with 1013. Thus a request's 16 MiB response-text limit can be cut short by the lower socket-wide output budget. Gateway retains at most one provider read at a time and rejects a source read larger than 2 MiB. These are application accounting and read bounds, not a guarantee about the Worker runtime's internal send queue: Workers exposes no dependable outbound drain signal. ACKs are client assertions; a malicious authenticated direct WebSocket peer can ACK chunks it did not consume and release the tracked pending-frame budget. The 8 MiB lifetime cap still limits total bytes Gateway attempts to send, but does not prove that the runtime has drained them. The adapter is trusted to ACK only after its local response writer accepts the data. Gateway does not rely on `bufferedAmount`. When no request is active, the socket has a 60-second idle timeout, independent of token expiry; each upstream response read also has a 60-second idle timeout.

### Cancel a request

```json
{
  "event": "request.cancel",
  "requestId": "3a0d1ae4-6c1d-4f4a-9c93-b5be26646a01"
}
```

Cancel aborts the upstream fetch and reader. If the attempt is active, Gateway emits one `response.error` with `code="cancelled"` and the current `lastSeq`. A stale cancel for a known terminal request is an idempotent no-op. A cancel for an unknown ID is ignored; it does not create work. If the socket disconnects, Gateway cancels every active upstream request. Because a disconnected peer cannot receive a terminal frame, the adapter treats missing terminal output as an interrupted attempt, never as successful completion.

## Terminal states, ordering, and reconnects

For each accepted start, while the connection remains usable, Gateway emits exactly one terminal event: `response.end` or `response.error`. Chunks for one request have contiguous increasing sequence values. WebSocket ordering preserves the order Gateway sends for each connection, but chunks from different request IDs may interleave. No chunk follows the terminal event. A terminal response can arrive before the adapter finishes writing earlier chunks; the adapter waits for all preceding sequence numbers and local writes before reporting the local SSE result.

At 30 seconds before token expiry Gateway sends `session.draining` with `reason="token_expiring"`. At expiry it refuses new starts with `session_expired`; ACK and cancel frames remain accepted for existing work, including ACKs for terminal attempts whose sent chunks are still unacknowledged. Token expiry alone does not cancel a request already authorized. Such a request may continue only until the earlier of its 300-second request deadline and the hard `maxSessionSeconds` socket lifetime. When the session cap is reached, Gateway sends policy draining and closes the socket, cancelling all active work. A close before a request terminal frame is an interrupted attempt and may already have incurred a provider charge; the adapter reports that uncertainty and any retry uses a new request ID. Gateway has no resume/replay cache and never silently retries.

## Local adapter requirements

The adapter's OpenAI-compatible HTTP API is a separate local boundary. Bind only to loopback, require a local bearer secret, reject non-loopback Host/Origin values, and do not use browser cookies as authorization. Stream Gateway `data` into the local SSE response, preserve upstream event content for the adapter's provider translator, and send ACK only after local output has been consumed as described above. A client disconnect or cancellation sends `request.cancel`; cancellation must reach the Gateway and upstream fetch. Do not log prompts, responses, keys, tokens, or envelopes.

## Custom provider configuration

An administrator can register an immutable public HTTPS API root using the OpenAI-compatible protocol. The provider ID remains the credential and authorization identity; `protocol` selects payload and SSE translation independently. Bootstrap model entries include `protocol`; adapter 0.2.0 requires it for custom provider IDs, while legacy built-in entries can infer their protocol. The Base URL stays in the server registry and is never accepted in request frames. Custom DNS is validated during registration, re-enabling, connection tests and before Gateway decryption; redirects are rejected. DNS validation does not pin the later upstream connection.

## Generation operation selection (ADR 0003)

A normal `request.start` may include `api: "chat.completions" | "responses" | "completions"`. Missing `api` retains the previous Chat Completions behavior. This enum selects only the fixed upstream suffix inside the provider registry Base URL. It does not accept a URL, arbitrary path or protocol. ACKs are unchanged. OpenAI-protocol providers support the three operations; Anthropic supports only `chat.completions` (mapped to Messages). All operations retain credential ownership, live authorization, custom DNS checks and cancellation/ACK limits.

Responses requests are stateless on both adapter and Gateway: storage is false; background generation, previous-response/conversation handles and item references are rejected. Native typed Responses events are forwarded as opaque chunks by Gateway, while the adapter validates SSE lifecycle, preserves output/tool/reasoning/usage fields and rewrites provider model names to the local alias. A successful terminal is released only after Gateway completion. Buffered calls return the final Response object. No GET/DELETE object storage contract is exposed. See [ADR 0003](decisions/0003-client-generation-apis.md) and [adapter usage](../apps/adapter/README.md).
