# ADR 0004 — Administrator updates to custom provider Base URLs

Date: 2026-10-18. Status: accepted following the owner's explicit request. Supersedes endpoint immutability in ADR 0001 for custom providers only.

System administrators may update a custom provider's Base URL using the existing PUT route. Provider ID and protocol remain immutable; built-in OpenAI/Anthropic routes remain fixed. The update body is `{baseUrl,expectedBaseUrl}`; enable/disable retains its separate `{enabled}` body. The expected URL is a compare-and-swap precondition preventing lost updates. Normalize and validate HTTPS, forbidden service origins and public DNS before saving, then recheck the administrator's live allowlist/session at commit time. Apply the existing update rate limit and CSRF boundary.

Same-origin path changes retain credential envelopes, IDs, model mappings and grants; this supports standard-to-Go paths on the same provider host without re-entering the key. A cross-origin change atomically revokes all existing credentials for that provider before updating the route. Old envelopes therefore cannot send an existing key to a new host; users must enroll credentials for the new origin. The UI explicitly confirms the old/new route and the consequence before submitting. Cross-origin credential revocation is global to this provider, matching its global registry scope. Administrative changes are audited with route metadata and revocation count, never keys/envelopes.

Use an atomic D1 batch for the conditional route write and any credential revocations. The next request/connection test reads the new registry route; already authorized/in-flight requests retain the existing bounded completion/cancellation policy. DNS checks still cannot pin TLS resolution. An update never selects a client-controlled request URL, changes model permissions, or retries an LLM call. No live provider configuration is changed merely by deploying this feature.

Validate same-origin reuse, cross-origin revocation (including old-envelope rejection), admin/CSRF/session checks, URL/private-DNS rejection, stale writes, enable/disable compatibility and browser form behavior. Update operational guidance to replace the superseded immutable-endpoint instructions.

Custom-provider credential enrollment also requires `expectedBaseUrl` from the route displayed by the client. Missing or mismatched expectations fail with `409 provider_conflict`, including submissions from a stale UI after a retarget. The final credential INSERT conditionally rechecks the same enabled provider route after encryption, preventing an in-flight old-route enrollment from becoming active after a cross-origin revocation batch. Built-in credential enrollment remains compatible without the extra field. On conflict, clients refresh the route and ask the user to re-enter the key; they never silently resubmit it to a changed destination.

Go compatibility follow-up: on the exact `https://opencode.ai/inference/go/` origin/path only, Gateway identifies itself as `ws-llm-cloudflare-proxy/0.1.0`, uses Accept application/json (the upstream stream remains explicitly enabled), and supplies a random opaque session UUID stable for the WebSocket connection. This bounded connection scope groups multiplexed work without disclosing account/token IDs; reconnect starts a new provider session. It is not a persistent conversation identifier. The adapter preserves caller reasoning_effort rather than imposing a provider-specific default globally. Authorized Go probes can explicitly request max effort with a larger output budget.
