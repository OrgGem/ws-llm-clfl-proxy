# ADR 0001: Phase 1 implementation contracts

- Status: accepted for the MVP implementation
- Date: 2026-10-17
- Scope: shared contracts for Identity, Gateway, and the local adapter

## Decisions

### Runtime and packages

Use TypeScript and npm workspaces. Put wire schemas, JWT claim types, credential-envelope types, and protocol constants in the shared package so Identity, Gateway, and the adapter consume one contract. Validate all network input at runtime; TypeScript types alone do not validate frames.

Use the maintained `jose` package for ES256 JWT signing and verification. Identity is an issuer of short-lived machine access tokens for this application; it is not an OpenID Connect identity provider. User login remains OIDC with the configured external provider, using a maintained OAuth/OIDC client library such as `oauth4webapi` for authorization-code/PKCE, state, nonce, and callback validation. Do not implement discovery, userinfo, or an OIDC issuer in this MVP.

### Principal, machine tokens, and revocation

An allowlisted OIDC `(issuer, subject)` identifies the user. A client/session delegates that user into one project. A Gateway JWT's protected JOSE header has `alg=ES256`, `typ=JWT`, and a required `kid`. Its claims are `iss` equal to the configured machine-token issuer, `aud=llm-socket-gateway`, `sub=userId`, `sid=sessionId`, `project_id`, `client_id`, `jti`, `iat`, `nbf`, and `exp`. Timestamps are integer Unix seconds. Access-token lifetime is five minutes. Identity verifies the signature and key ID against its configured public JWKS, pins `ES256`, and validates issuer, audience, and time claims with at most five seconds of clock tolerance. Gateway receives verified claims only over the private Identity binding and independently validates their shape, issuer, audience, and timing; it enforces `exp > now` strictly for every handshake and request start, so clock tolerance never extends authorization to start new work.

The configured bootstrap email can create the first administrator only when the allowlist has never contained an administrator row. The check is keyed by exact issuer and subject, and any previous admin row permanently consumes bootstrap, even after revocation; matching an email does not authorize a different subject. Confidential client secrets and client model grants are managed by the creating user. Project owners and project admins may revoke clients in their project; ordinary project members cannot. Project managers cannot rotate another user's secret or take over its machine-token principal. Public clients are created only through an approved pairing request and never receive a shared client secret.

The active private signing key is a Worker Secret. Identity serves public verification keys from `MACHINE_JWT_PUBLIC_JWKS` at the fixed `/.well-known/jwks.json` endpoint (also available at `/.well-known/jwks`); the issuer is explicitly configured as `MACHINE_ISSUER`. The endpoint returns public keys only and sets a 60-second cache lifetime. Rotation publishes the new key before signing with it and retains the old public key until five-minute tokens, five seconds of clock tolerance, and the JWKS cache lifetime have expired. `kid` selects a key; a missing or unknown `kid` fails closed. JWKS is a key-distribution endpoint, not evidence that the service implements OIDC.

Claims identify the principal and delegation but do not freeze authorization. On every `request.start`, Gateway calls Identity over a private Service Binding. Identity verifies the bearer token again, derives identity from its claims, and checks active session, client, user, project ownership, credential state, provider permission, and model permission in D1. It returns authorization and credential metadata only, never a raw provider key. Credential/session revocation applies to the next request start. A request already authorized may finish or be cancelled by its normal timeout/disconnect policy; this MVP does not promise cancellation of an in-flight provider call at the instant a D1 row changes.

Refresh credentials are opaque random values of at least 256 bits. Store only a cryptographic hash in D1, rotate on every successful refresh, and enforce a 30-day absolute session lifetime. Public clients do not receive a client secret. A one-time pairing code, approved by an allowlisted user in the authenticated browser UI, binds a local client to that user's project. Pairing codes expire within ten minutes, are single-use, rate-limited, and display the client/device being approved. Pairing delegates an app session; it is not a custom OAuth or OIDC issuer.

### Provider credential envelope

Identity encrypts submitted API keys with AES-256-GCM. Use a fresh cryptographically random 96-bit nonce for every encryption. The Worker Secret key is identified by a non-secret `kid`; retain old decryption keys while unexpired envelopes using them remain valid. The envelope expires after 30 days unless reissued. D1 stores credential ownership/provider/key-version/expiry/revocation metadata, not plaintext or ciphertext by default. The adapter stores the returned envelope locally; losing it requires re-entering the provider key.

The JSON wire object is `{v:1,alg:"A256GCM",kid,credentialId,userId,projectId,provider,exp,nonce,ciphertext}`. `exp` is integer Unix seconds. `nonce` and `ciphertext` are independently base64url-encoded without padding; Web Crypto's AES-GCM ciphertext contains the 16-byte authentication tag appended to encrypted bytes. Provider key plaintext is exact UTF-8 bytes and is capped at 8 KiB. AAD is the exact UTF-8 byte sequence `v1\n${credentialId}\n${userId}\n${projectId}\n${provider}\n${kid}\n${exp}`, with `exp` rendered as unsigned base-10 integer text. To keep newline-delimited AAD unambiguous, generated `credentialId`, `userId`, and `projectId` match `^[A-Za-z0-9._:-]{1,128}$`; configured provider IDs match `^[a-z0-9][a-z0-9_-]{0,63}$`; configured key IDs match `^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$`. These fields exclude newline, are generated or configured by the service, and are not raw OIDC subjects or caller-controlled strings. AAD binds owner, project, provider, key version, and expiry. The Gateway compares the authenticated envelope metadata to Identity's D1 metadata and the JWT principal before calling a provider. An envelope is sensitive bearer material, not end-to-end encryption; Identity can decrypt it.

The adapter includes the envelope in every `request.start`, not in the WebSocket URL or handshake. This keeps credentials out of URLs and lets the Gateway perform fresh ownership, expiry, permission, and revocation checks for each operation. The Gateway decrypts only after those checks, keeps the raw key only for the provider call, and never returns it to the adapter.

### Custom provider BaseURLs and SSRF checks

The provider registry may contain administrator-managed custom endpoints using the OpenAI-compatible or Anthropic request protocol. The initial UI creates custom OpenAI-compatible providers only; it does not accept an endpoint URL in a model request. Identity accepts system-admin-only `POST /api/providers` with `{id,displayName,baseUrl,protocol:"openai"}`; custom IDs match `^[a-z][a-z0-9_-]{0,31}$`. A custom provider record binds this stable ID to its protocol and normalized BaseURL. This original immutable-endpoint decision is superseded for custom Base URLs by ADR 0004: administrators may update routes with compare-and-swap/live authorization; same-origin changes preserve envelopes and cross-origin changes atomically revoke all provider credentials. ID and protocol remain fixed; providers can still be disabled. Credential envelopes remain bound to provider ID, so a saved key cannot be silently redirected to another host. Provider/model records and adapter bootstrap model entries carry `{id,provider,protocol}` so the adapter uses the protocol selected by the trusted registry.

Shared exports are `normalizeBaseUrl(input, {forbiddenOrigins})`, `buildProviderEndpoint(protocol, baseUrl)`, and `assertPublicEndpointResolution(endpoint, fetcher?)`. Normalization accepts HTTPS only; rejects userinfo, query, fragment, non-default ports, IP literals (including URL-normalized IPv4 forms and IPv6), single-label hosts, and local/internal/reserved names; and rejects caller-supplied exact Identity/Gateway origins. It returns the normalized path with exactly one trailing slash, preserves an explicit root path, and does not silently add `/v1`; a bare origin remains at `/`. A bounded path prefix may be used, but percent characters are rejected to rule out encoded separators and traversal. A BaseURL that already ends in `/chat/completions` or `/messages` is rejected, because clients configure the API root rather than an operation endpoint. Endpoint builders append only the fixed `/chat/completions` or `/messages` route for the selected protocol. Public platform hostnames are not blanket-blocked; exact service origins are supplied by the caller, and DNS results are checked. The Gateway never accepts a URL or protocol override from `request.start`.

Identity validates and resolves a custom BaseURL before saving it and during custom provider connection tests. Gateway's `authorizeTokenRequest` response includes the D1-derived `authorizedProvider:{id,displayName,protocol,baseUrl,custom}` metadata; Gateway repeats the DNS check for every custom call before decrypting the credential. The check uses a fixed Cloudflare DNS-over-HTTPS endpoint to request A and AAAA records in parallel, with a five-second timeout per query, redirects rejected, and a 64 KiB response cap. DNS errors, NXDOMAIN, truncated or malformed answers, any non-global-unicast A/AAAA address found in either response, or the absence of all public A/AAAA answers fail closed; an empty successful response for one address family is allowed when the other has public answers. `ipaddr.js` classifies IPv4 and IPv6 special ranges, including rejecting all IPv4-mapped IPv6 answers, plus transition, reserved, multicast, link-local, and carrier-grade NAT ranges. Built-in OpenAI and Anthropic endpoints remain exact server constants and skip per-request DNS checks.

The DNS guard does not pin the resolved address into the TLS connection. Workers `fetch()` resolves the hostname again, so DNS can change between validation and connection; the recheck reduces rebinding exposure but cannot eliminate this time-of-check/time-of-use gap. Custom endpoints are therefore an administrator-trusted capability, not a guarantee that arbitrary public hostnames are safe. Keep redirects disabled, limit registration and changes to system administrators, and reject loopback/private/reserved resolution at both registration and every Gateway call.

### WebSocket and stream contract

The adapter opens WSS with `Authorization: Bearer <machine JWT>` and subprotocol `llm-proxy.v1`. Do not put tokens in a URL. After signature/session validation, Gateway sends `session.ready`; failed authorization is rejected before upgrade when possible, otherwise the socket closes with policy code and no `session.ready`.

Frames are UTF-8 JSON text objects with an `event` discriminator. The v1 event names are exactly `session.ready`, `request.start`, `response.chunk`, `response.end`, `response.error`, `request.cancel`, and `session.draining`. Initial schemas and hard bounds are in [PROTOCOL.md](../PROTOCOL.md). A normal `request.start` contains a UUID `requestId`, provider ID, model alias, envelope, and provider-specific JSON `payload` created by the adapter; it contains no endpoint URL. Gateway chooses the upstream URL and model mapping from server-side configuration and injects the mapped model and streaming flag.

Retries are new attempts with new request IDs. Gateway never retries a provider call. A disconnect before `response.end` is an interrupted attempt; the client must surface that outcome and must not merge a retry into the prior stream. Errors expose whether the upstream fetch was started because it may already have processed or billed the request.

Workers do not provide a dependable application-visible WebSocket drain signal for this design. Gateway tracks at most 4 MiB of unacknowledged serialized response-chunk frames per socket and sends at most eight unacknowledged chunks per request. The v1 schema allows chunks up to 32 KiB of UTF-8 text; Gateway currently emits at most 16 KiB per chunk and pauses upstream reads when the window is full. The adapter sends a cumulative ACK using the `op:"ack"` variant of `request.start` only after corresponding bytes have been consumed by its local response writer. ACKs after a terminal frame are still processed while earlier chunks remain outstanding; this releases the tracked pending-frame budget. ACKs are client assertions: a malicious authenticated direct WebSocket peer can acknowledge chunks it did not consume, so the 4 MiB pending-frame bound assumes the trusted adapter ACKs honestly. Gateway also enforces a separate 8 MiB cumulative serialized outbound-frame budget per socket lifetime, including control and terminal frames; ACKs never refund it. Gateway reserves room for a policy-draining frame when possible, then aborts active requests and closes with code 1013 at that cap. The cap can interrupt the 16 MiB per-request response-source limit first. Neither this lifetime accounting nor protocol ACKs prove that the Worker internal WebSocket queue has drained. If the oldest outstanding chunk remains unacknowledged for 15 seconds, Gateway cancels upstream, sends a `slow_client` error when possible, announces policy draining, and closes the entire socket with code 1013. It does not claim `bufferedAmount` is available or reliable in Workers.

### Limits and provider routing

Hard limits are: 1 MiB maximum `request.start` JSON frame; 4 KiB maximum control frame; eight active requests per socket; eight unacknowledged response chunks per request; 32 KiB schema limit per response chunk; 256 KiB maximum serialized response chunk frame; 4 MiB tracked unacknowledged serialized response-chunk frames per socket; 8 MiB cumulative serialized outbound frames per socket lifetime including controls and terminal frames; 16 MiB provider response text per request; 15-second acknowledgement timeout; 60-second provider read idle timeout; 60-second socket idle timeout while no requests are active; 300-second request deadline; five-minute token lifetime; and a 300-second maximum socket lifetime. ACKs refund the tracked 4 MiB pending budget, never the cumulative 8 MiB cap. Gateway reserves control-frame space for policy draining when possible, then closes with 1013 and aborts active work at the lifetime cap; the request source limit may be cut short by the socket-wide output cap. Per-project settings can lower provider-body size (1 KiB–1 MiB), per-socket concurrency (1–8), and socket lifetime (30–300 seconds). The provider-body size is measured as UTF-8 JSON bytes after Gateway injects the authorized upstream model and `stream:true`, excluding the envelope and WebSocket framing. `session.ready.maxInFlight`, `maxPayloadBytes`, and `maxSessionSeconds` report those effective project limits. The token authorizes new starts only through expiry. Send `session.draining` 30 seconds before expiry and stop accepting new starts at expiry; requests already authorized may continue only until the earlier of their own 300-second deadline and the hard socket lifetime. At the session lifetime cap, Gateway closes the socket and cancels active work. A socket is limited to 1,024 distinct request IDs over its lifetime; once reached, drain and reconnect.

Provider IDs, model aliases, model permissions, endpoint URLs, paths, and authentication-header rules are server-controlled registry data. A client cannot supply a URL, hostname, path, redirect target, or auth header. MVP provider routing uses exact configured HTTPS endpoints, does not follow redirects, overrides the upstream model with the authorized alias mapping, and requires streaming. Custom endpoints require explicit administrator allowlisting and SSRF review. Do not log request payloads, upstream response bodies, provider keys, access/refresh tokens, or envelopes.

### Local adapter boundary

The local HTTP adapter binds only to loopback (`127.0.0.1` and/or `::1`), including when running in ChatGPT Cloud; it is part of the client deployment. It uses a local bearer secret with restrictive local storage, validates the Host/Origin boundary, and does not rely on browser cookies for local API authorization. Its SSE writer propagates cancellation upstream and waits for local writable drain before acknowledging WebSocket chunks.

## Consequences and known limits

Identity remains the authorization data owner and the only component that needs D1 for per-request authorization. Gateway uses the private `IdentityInternal` WorkerEntrypoint Service Binding. The Gateway Wrangler config uses `[[services]]`, `binding = "IDENTITY"`, and `entrypoint = "IdentityInternal"`; the configured service name is `ws-llm-identity` for local/default and `ws-llm-identity-staging` for staging. `IdentityInternal extends WorkerEntrypoint<Env>` exposes `validateToken(accessToken)` for handshake authorization and `authorizeTokenRequest({accessToken,credentialId,provider,model})` for every request start. `validateToken` returns the verified principal and `tokenExpiresAt`; `authorizeTokenRequest` derives the principal from the token and returns `{allowed:true,principal,credentialMetadata}` or `{allowed:false,reasonCode}`. It never returns a raw key. Public `/internal/*` HTTP paths return 404; this RPC is not exposed as a public route. A D1 binding does not provide row-level or read-only permissions; if a Gateway D1 binding is later introduced, it must be treated as privileged and constrained in code and deployment.

The per-socket bounds do not implement an exact account-wide concurrency quota. Multiple sockets can exceed these per-socket limits unless a separate atomic coordinator is added. Workers Free CPU/subrequest limits and real stream capacity require measurement; no capacity guarantee follows from the selected limits. Benchmarks and any unverified provider/runtime behavior remain Phase 1 evidence to collect, not assumed facts.
